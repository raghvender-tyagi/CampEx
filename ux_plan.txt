Why this pattern
UI element

Listing card

• Title (1 line, truncated)

Listing card
• Same structure
• "For rent" badge if rental type
Section label — "Latest listings"
• Infinite scroll grid below, 2 columns
Bottom navigation bar (sticky)
• Home — Categories — [+] Post (center, raised) — Wishlist — Profile

Why this pattern
UI element
Behaviour / why it's designed this way
Search bar is tap-only (not focus-on-load)
Tapping opens a dedicated search screen with keyboard — avoids layout jump, same as Instagram/Amazon search entry pattern
Category icons before listings
Lets users self-filter by intent immediately ("I want furniture") instead of scrolling everything — core OLX/Facebook Marketplace pattern
"Near your hostel" personalization
Uses profile data (Phase 1) to surface relevant local listings first — increases relevance, reduces irrelevant scroll
Heart icon directly on card
One-tap save without opening the listing — reduces friction, standard e-commerce pattern (Amazon, Flipkart wishlist)
Floating [+] Post button in bottom nav
Center-raised button is the single most prominent CTA — sellers are the supply side, so posting must be effortless to reach from anywhere
2-column grid, not list
Mobile-first marketplaces always use grid for browsing (visual scanning is faster than reading list rows) — list view reserved for search results only

Why this pattern
UI element
Behaviour / why it's designed this way
Sub-category chips, not a new screen

Result count shown
Builds trust in the filter system — user sees the filter actually changed something ("142 results" updates live)
Empty state has a CTA, not just an apology
Converts a dead-end into a seller opportunity — turns "nothing here" into "you could post here"

PAGE 6   Listing detail page

Ye sabse important page hai — yahin user decide karta hai ki contact kare ya nahi. Iska layout sabse zyada thought-through hona chahiye.

Layout — top to bottom
Image carousel (swipeable, full-width)
• Dot indicators below
• Back arrow + Share + Report icon overlaid top
Title + Price (large, bold)
• Status badge if sold/rented (e.g. greyed "SOLD" ribbon)
Quick info chips
• Condition • Category • Posted 2 days ago • 34 views
Description section
• Full text, "Read more" if long
Location row
• Map pin icon + "Hostel B, Block 2"
Seller card
• Avatar + Name + Branch/Year
• Star rating + review count
• "View Profile" link
• "Member since 2024"
Similar listings (horizontal scroll)
• "You may also like" — same category
Sticky bottom action bar
• Heart icon (wishlist) + Chat icon (message) + Primary button: "Contact Seller" or "Request Rental"

Why this pattern
UI element
Behaviour / why it's designed this way
Sticky bottom action bar
The CTA (contact/request) must always be reachable without scrolling back up — this is the page's entire conversion goal, never let it scroll out of view
Seller card with rating visible here
Trust signal shown at the decision moment, not buried in a separate tap — buyers decide partly based on seller reputation (Phase 5 reviews feed directly into this card)
"34 views" social proof
Mild urgency signal without being manipulative — shows the item is in demand
Report icon always visible
Moderation must be one tap away on every listing — never nested in a menu, this is a safety-critical action
Status badge (SOLD) overlays but doesn't hide
Sold items stay visible for transparency/history but are clearly non-actionable — button changes to disabled "No longer available"
Contact Seller vs Request Rental — button text changes
Same page template serves both sell and rent listings; the CTA text adapts based on listing_type — avoids building two separate detail pages

PAGE 7   Create listing (multi-step)

Multi-step form, ek baar mein ek cheez — taaki form lamba/daunting na lage. Top pe progress bar.

Step 1 of 4 — What are you posting?
Progress bar (4 dots/segments, step 1 filled)
Listing type selector — 4 large tappable cards
• Sell  |  Rent  |  Exchange  |  Give away free
Category grid (tap to select)
• Same icons as Home feed

Step 2 of 4 — Photos & details
Photo upload grid
• Up to 8 photo slots, first photo marked "Cover"
• Drag to reorder, tap [+] to add
Title field
• Character counter (e.g. 12/80)
Description textarea
• Placeholder with example text shown as hint
Condition selector — chip group
• New / Like New / Good / Fair

Step 3 of 4 — Price & location
Price input (large, numeric keypad)
• If "Rent" selected in step 1: shows Daily/Weekly/Monthly rate tabs instead
"Negotiable" toggle
Location — auto-filled from profile hostel
• Editable dropdown

Step 4 of 4 — Review & post
Live preview card
• Exactly how it will appear in the feed
Edit links next to each section
• Tap to jump back to that step
Primary button — "Post Listing"

Why this pattern
UI element
Behaviour / why it's designed this way
4 short steps instead of 1 long form
Reduces perceived effort and abandonment — same pattern as OLX/Airbnb listing creation, each screen asks 2-4 things max
Type selected first (step 1)
Determines which fields appear later (e.g. rent duration only shows for rentals) — branching logic decided early, not buried mid-form
Live preview before posting (step 4)
Lets the seller see exactly what buyers will see — catches typos/bad photos before going live, reduces edit-after-post rate
Photo upload first in step 2
Listings with photos get drastically more engagement — prioritizing photo upload nudges sellers to add them before writing text
Auto-filled location from profile
Reduces repetitive typing — most students sell from their own hostel, override available but not required

PAGE 8   My listings dashboard

Layout — top to bottom
Header — "My Listings" + [+] New button
Status tabs
• Active (8)  |  Sold (3)  |  Rented (1)  |  Pending Approval (1)
Listing row (list view, not grid)
• Thumbnail + Title + Price (left)
• Views count + Wishlist count (middle, small)
• 3-dot menu: Edit / Mark Sold / Boost / Delete (right)
Rental requests badge on relevant listings
• Small red dot: "2 new requests"

Why this pattern
UI element
Behaviour / why it's designed this way
Status tabs instead of one long list
Sellers think in terms of "what's still active vs done" — tabs match mental model, same pattern as Amazon Seller Central / OLX "My Ads"
3-dot menu for actions, not buttons inline
Keeps the row scannable — destructive actions (delete) are intentionally one tap deeper to prevent accidental taps
Rental request badge surfaced here
Sellers manage all their listings from one place — they shouldn't have to remember to check notifications separately for each item
List view here, grid view on Home
Sellers managing their own items need to scan title/price/stats quickly (list = faster scanning); buyers browsing need visual recognition (grid = faster visual scan)

UI element

Listing context card pinned in chat

Quick reply chips for first-time message

Unread dot in inbox list, not a number badge
Simple presence indicator is enough at list level; exact count matters more at the app icon/notification level

UI element

UI element

PAGE 17   Admin dashboard (internal)

Ye web-based hota hai (desktop layout), students wali app se alag — Django admin ko customize karke banega.

Layout — top to bottom (desktop)
Top stat cards (4 across)
• Total Users | Active Listings | Pending Reports | Pending Approvals
Left sidebar navigation
• Users | Listings | Categories | Reports | Reviews | Settings
Main panel — data table
• Sortable columns, search bar, bulk-select checkboxes
• Row actions: View / Approve / Suspend / Delete
Reports queue (priority view)
• Reported listing/user + reason + reporter + "Review" button

Why this pattern
UI element
Behaviour / why it's designed this way
Stat cards at top
Gives moderators an at-a-glance health check before diving into specific records — every admin tool (Stripe, Shopify, Django admin itself) leads with summary metrics
Bulk-select + bulk actions
Moderators handle volume (e.g. approving 30 listings) — one-by-one actions don't scale, bulk actions are essential at any real user count
Reports queue separated from general listing table
Time-sensitive moderation work needs its own prioritized view, not buried in a generic "all listings" table sorted by date

End-to-end user flow
Pura journey ek naye user ka, signup se le ke successful sale tak:

1.  Splash screen → taps "Get Started"
2.  Registers with college email → verifies via email link
3.  Lands on Home Feed → browses categories or searches
4.  Taps a listing → views Listing Detail page → checks seller rating
5.  Taps "Contact Seller" → Chat thread opens with quick-reply chips
6.  Negotiates in chat → seller marks item as Sold once deal is done
7.  Buyer leaves a review on Seller Profile → builds trust for future listings

Aur seller-side parallel flow:

1.  Taps [+] Post button from bottom nav (always reachable)
2.  4-step Create Listing flow → reviews live preview → posts
3.  Listing appears in Home Feed (after optional admin approval)
4.  Receives chat messages / rental requests via Notifications
5.  Manages everything from My Listings Dashboard

Core design principles used throughout
Bottom nav [+] Post button, sticky Contact Seller bar on Listing Detail: Every primary action is sticky/always-reachable
Buyers scan visually (grid); sellers/admins scan data (list/table): Grid for browsing, list for managing
Verified badge, ratings, member-since all visible before the buyer commits to messaging: Trust signals surfaced early, not buried
Filters, rental requests, claim forms — keeps context without full page navigation: Bottom sheets for secondary actions
Create Listing, Roommate Preference — reduces perceived effort: Multi-step forms for anything with 4+ fields
Sold/Active/Pending badges use consistent colors across every screen so users learn the system once: Color-coded status everywhere
Never just "nothing here" — always paired with a CTA to fix it: Empty states always have a next action
